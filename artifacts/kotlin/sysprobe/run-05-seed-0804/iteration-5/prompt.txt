You are refining a Hypothesis strategy to find behavioral divergence between four Kotlin JSON deserializers.

Record schema (all six fields always present in a well-formed document):
{
  "id": <integer>,
  "amount": <string>,
  "name": <string or null>,
  "status": <one of "active", "inactive", "unknown">,
  "tags": <array of strings>,
  "child": <Record or null, one level of recursion normally>
}

Four independent Kotlin JSON deserializers are run against every document you
produce, each at its default configuration and each decoding into the same
Kotlin data class: Gson, Moshi (generated adapter), kotlinx.serialization,
and Jackson with its Kotlin module. Your goal is to produce documents that
make these four implementations disagree with each other -- one accepting
where another rejects, or two accepting but decoding to different values.

What is already known about these four implementations, from running
probe documents against them before any fuzzing (use it however you see
fit):
1. Gson accepts missing non-nullable fields, decoding missing integers as 0, missing strings as null, and missing enums as null; Moshi and kotlinx.serialization reject missing required fields; Jackson rejects missing non-nullable fields except it accepts missing "child".  
2. Gson and Jackson accept null for non-nullable integer "id" (decoding as 0); Moshi and kotlinx.serialization reject null for "id".  
3. Gson accepts null for non-nullable string "amount" as null; Moshi, kotlinx.serialization, and Jackson reject null for "amount".  
4. Gson, Jackson, and Moshi accept integer values for string "amount", coercing to strings; kotlinx.serialization rejects it.  
5. Gson accepts unknown enum values for "status" as null; Moshi, kotlinx.serialization, and Jackson reject unknown or case-variant enum values.  
6. Gson and Jackson accept missing "tags" and "child" fields as null; Moshi rejects missing "tags"; kotlinx.serialization rejects missing "tags" and "child"; Jackson accepts missing "child" but rejects missing "tags".  
7. Nested objects behave like top-level: Gson and Jackson accept null or missing non-nullable fields inside "child"; Moshi and kotlinx.serialization reject them.  
8. Gson and Jackson accept integer "amount" inside nested "child", coercing to string; Moshi accepts it; kotlinx.serialization rejects it.  
9. Gson accepts null "amount" inside nested "child"; Jackson rejects it.

Strategy hint: implementations are more likely to disagree on documents that
are *almost* well-formed with one specific thing off (a field of the wrong
type, a field missing rather than present-but-wrong, a value at a type
boundary) than on documents that are broadly malformed in many ways at once
-- broad malformation tends to make every implementation reject identically,
which scores zero. Vary one or two things about an otherwise valid document
at a time, across many documents, rather than maximizing how unusual any
single document looks.
