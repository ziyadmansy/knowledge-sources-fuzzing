Record schema (all six fields always present in a well-formed document):

  "id": <integer>,
  "amount": <string>,

Four independent Kotlin JSON deserializers are run against every document you
produce, each at its default configuration and each decoding into the same
Kotlin data class: Gson, Moshi (generated adapter), kotlinx.serialization,
and Jackson with its Kotlin module. Your goal is to produce documents that
make these four implementations disagree with each other -- one accepting
where another rejects, or two accepting but decoding to different values.

What is already known about these four implementations, from running
probe documents against them before any fuzzing (use it however you see

1. All four accept fully well-formed documents with correct types (Probe 1).

2. All four accept numeric "id" as either integer or string convertible to integer (Probes 2, 9).

3. Gson, Moshi, and Jackson accept "amount" as string or number, converting number to string; kotlinx rejects number (Probes 3, 13, 15).

4. Gson and Moshi accept "name" as string or number (converted to string); kotlinx rejects number; Jackson accepts number converted to string (Probes 4, 16).

5. For "name": null is accepted by all (Probes 1, 5).

6. For "status", only exact enum strings "active", "inactive", "unknown" accepted; Moshi, kotlinx, Jackson reject others; Gson accepts but decodes invalid as null (Probes 5, 17).

7. "tags" must be an array; string instead causes rejection by all (Probe 6).

8. "tags" array elements must be strings or convertible; Gson, Moshi, Jackson accept numbers (Moshi rejects booleans); kotlinx rejects non-string elements (Probes 7, 14).

9. "child" can be null or full Record; empty object {} accepted only by Gson (with defaults), rejected by others (Probe 12).

10. Extra fields cause rejection by kotlinx and Jackson, acceptance by Gson and Moshi (Probes 10, 19).

11. Missing fields inside nested "child" cause rejection by Moshi, kotlinx, Jackson; Gson fills with defaults (Probe 12).

12. Duplicate keys: last occurrence wins for all (Probe 20).

Strategy hint: implementations are more likely to disagree on documents that
are *almost* well-formed with one specific thing off (a field of the wrong
type, a field missing rather than present-but-wrong, a value at a type
boundary) than on documents that are broadly malformed in many ways at once
-- broad malformation tends to make every implementation reject identically,
which scores zero. Vary one or two things about an otherwise valid document
at a time, across many documents, rather than maximizing how unusual any
single document looks.
