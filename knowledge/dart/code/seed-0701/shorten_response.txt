1. Manual uses `as int` for `id`, rejecting floats (e.g. 1.0); json_serializable/freezed cast `(num).toInt()`, accepting integral floats.

2. Manual and json_serializable/freezed accept `name: null` or string; built_value omits `name` if null but accepts null if present.

3. Manual’s `status` uses `Enum.values.byName` throwing raw `ArgumentError` on unknown strings; json_serializable/freezed use `$enumDecode` throwing `CheckedFromJsonException`; built_value’s `valueOf` throws `ArgumentError` wrapped in `BuiltValueNestedFieldError` if nested.

4. Manual casts `tags` as `List` then each element as `String`; json_serializable/freezed cast as `List<dynamic>` then map to `String`; built_value expects non-null `BuiltList<String>`. All reject non-string elements or missing/null `tags`.

5. Manual and json_serializable/freezed accept `child: null` or nested object; built_value’s builder requires `child` null or valid `BvRecord`. If `child` present but not a map/object, all reject.

6. Enum decoding is case-sensitive exact match in all; no unknownEnumValue fallback.

7. Manual’s `id` and `amount` require exact types (`int` and `String`), no coercion; json_serializable/freezed coerce `id` from `num` to `int`; built_value likely requires exact types.

8. Missing `name` treated as null by all; built_value omits null `name` on serialization.

9. Missing or null `tags` rejected by all.

10. Recursive parsing of `child` consistent across all; built_value may throw `BuiltValueNestedFieldError` on nested failures.

Summary:  
- Manual is strict on `id` type (int only), enum decoding (raw `ArgumentError`), and `tags` type (List only).  
- Json_serializable/freezed accept numeric `id` (coerced), throw documented exceptions on enum errors.  
- Built_value requires exact types, throws wrapped errors on nested failures, omits null `name` and `child` on serialization.  
- Key divergences: `id` numeric coercion and enum error exception types.
