1. All four implementations accept fully well-formed records (Probe 1, 4, 11, 13, 15, 19).
2. All reject when a required field is present but of the wrong type (e.g., "id" as string, "amount" as int, "tags" as string, "tags" with non-string element, "child" as non-object or empty object, "name" as int, nulls for required fields) with _TypeError or DeserializationError (Probes 2, 3, 5, 7, 8, 9, 10, 12).
3. All reject when a required field is missing, except for "name" and "child", which can be omitted and are treated as null (Probes 13, 15 accepted; 17, 18 rejected).
4. "status" missing: all but built_value reject; built_value accepts and fills "tags" as empty array (Probe 14).
5. "tags" missing: all but built_value reject; built_value accepts and fills "tags" as empty array (Probe 14).
6. "child" missing: all accept and treat as null (Probe 15).
7. "name" missing: all accept and treat as null (Probes 4, 13).
8. "amount" missing: all reject (Probe 18).
9. "status" with invalid value: all reject with ArgumentError or DeserializationError (Probe 6).
10. All ignore extra fields (Probe 11).
11. built_value always rejects with DeserializationError, never _TypeError or ArgumentError.
12. json_serializable and freezed sometimes reject with ArgumentError (e.g., missing "status", Probe 16).
13. Recursion in "child" works if well-formed (Probe 19), but fails if nested record is malformed (Probe 20).
